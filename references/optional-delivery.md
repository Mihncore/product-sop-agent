# 需求确认后的可选模块

只有当用户明确要求方案设计或 Demo 时读取并执行。发现新的需求矛盾时，更新需求判断报告后再继续。

## 方案设计

### 发散

默认给出 3 个机制上真正不同的方案；只有方案空间足够大或用户要求时扩展到 5–7 个。不得为了满足数量制造同义方案。

至少包含：

- 最小可行方案
- 平衡价值与成本的方案
- 能暴露不同关键假设的替代方案

按统一维度描述和比较：

```text
【核心机制】
【目标用户路径】
【对应的需求与证据】
【核心假设】
【用户价值 / 业务价值】
【成本与依赖】
【主要风险】
【最小验证方式】
```

可以给出推荐倾向和理由，但明确最终取舍权属于用户。用户偏好只能影响权重，不能自动消除风险。

### 收敛

融合方案时保留取舍过程，不把所有亮点无条件堆叠在一起。输出：

- 选择了什么
- 放弃了什么
- 为什么
- 哪项证据支持该选择
- 哪些假设仍需在 Demo 或实验中验证

最终方案必须逐项对应需求判断报告中的目标、范围和成功标准。

## Demo 产出

根据用户需要和当前环境能力选择单文件 HTML、现有项目实现或其他合适原型形式，不默认任何形式都必须使用单文件 HTML。

生成前确认：

- 核心用户路径
- 要验证的关键假设
- 必须可操作的交互
- 目标设备与尺寸
- 使用真实数据还是模拟数据

生成后验证：

- 核心路径可以完成
- 按钮和输入有明确反馈
- 覆盖必要的加载、空、错误和成功状态
- 桌面端或移动端适配符合目标
- 没有明显遮挡、溢出和不可点击区域
- 基础键盘操作和文字可读性可接受
- Demo 中的每个关键设计能对应需求或待验证假设

如果当前环境不能运行或查看 Demo，明确区分“已生成”和“已验证”，不得声称未经检查的交互可用。

## 回退规则

- 视觉或文案问题：留在 Demo 模块修改。
- 用户流程或功能机制问题：回到方案模块。
- 用户、场景、价值或问题定义发生变化：回到需求判断模块。

每次回退只更新受影响内容，同时保留变更原因，避免从头重复讨论。
