## 需求地图

把它作为动态检查框架，不要要求用户一次填写所有字段。

```text
【需求来源】谁提出、为什么现在提出
【目标用户】使用者、决策者、付费者、受影响者
【关键场景】何时发生、触发条件、频率
【当前行为】用户现在怎么解决、替代成本、满意程度
【问题定义】可观察的问题，不包含预设方案
【影响】不解决的用户、业务或运营后果
【证据】数据、访谈、工单、观察、转述或直觉
【目标】希望改变的行为、结果或指标
【范围】必须覆盖、暂不覆盖、明确不做
【约束】时间、预算、技术、组织、合规、隐私
【依赖】团队、系统、数据、运营或外部条件
【核心假设】需求成立所依赖但尚未证实的前提
【主要风险】最可能导致需求无效或项目失败的因素
【替代路径】不开发、流程优化、人工服务或其他产品方式
【成功标准】可观察、可衡量或可验证的结果
【待确认】仍会影响判断的问题
```

## 问题选择规则

只问答案可能改变判断或下一步行动的问题。按以下顺序排序：

1. 答案是否可能推翻需求？
2. 是否能区分两个互斥解释？
3. 是否会改变目标用户、范围或成功标准？
4. 是否能暴露高成本或不可逆风险？
5. 用户是否最适合回答，还是应该通过数据或研究验证？

避免：

- 已经回答的问题
- 只是让文档更完整、但不影响判断的问题
- 一次要求用户填写整张表
- 在需求尚未成立时过早追问界面或技术细节
- 可以直接从现有材料读取的问题

## 需求就绪度

使用“充足 / 部分 / 缺失”评估，不制造虚假的精确分数：

| 维度 | 判断重点 |
|---|---|
| 问题清晰度 | 是否描述真实问题而非预设功能 |
| 用户与场景 | 对象、触发条件和当前行为是否明确 |
| 证据强度 | 事实是否超越个案、转述或直觉 |
| 价值判断 | 用户价值和业务价值是否可解释 |
| 假设暴露 | 决策依赖的未知前提是否已列明 |
| 风险与约束 | 最大失败风险和硬约束是否明确 |
| 范围边界 | 做什么、不做什么是否可判断 |
| 成功标准 | 是否知道怎样证明需求被解决 |

就绪度不是为了阻止推进。如果组织必须在信息不完整时决策，应明确记录风险和验证计划。
